## 1. A project is a shared set with members
| Part | What it holds |
|---|---|
| **Project** | id, name (e.g. *Flying Objects*), owner, the model it builds (`FlyingObjects.01`), its `labelmap.txt`, its synonym table |
| **Members** | each person's name, role, joined-at time stamp |
| **Pictures** | the pairs `bird.1001.jpg` + `bird.1001.xml`, each saying who added it and from where (sensor · device · video) |
| **Record** | an append-only list of what happened: joined, added 31 pictures, boxed, reviewed, merged names — with who and when |

## 2. Roles (one person can hold more than one)
| Role | Can |
|---|---|
| **Owner** | invite and remove members, set roles, edit the label list, export the training set |
| **Contributor** | add pictures and video (all three ways in), draw boxes — **Level 1** |
| **Reviewer** | accept · fix · reject boxes — **Level 2** — and merge similar names; never on a box they drew |
| **Viewer** | look and count; nothing else (a class guest, a parent) |
A guest who has not signed in can add pictures to a public practice project only, never to a group project, and never review.

## 3. Adding members
1. **Invite by code or QR.** The owner opens *Members → Invite*, chooses a role, and gets a short code plus a QR, valid for a set
   time (e.g. 7 days) and a set number of uses. The repo already has this pattern: `inviteCode` and `admits` in
   `frontend/lib/drone-2525/si-pod.ts` (code from a seed, admit with a check and a time stamp) — reuse it, do not write a second one.
2. **Sign in to join.** The app already signs people in (Auth0). A member is a signed-in person, so "who drew this box" and "who
   reviewed it" are real names — and "the reviewer is not the labeler" can be checked.
3. **Remove or change role** at any time; a removed member's pictures and boxes stay, with their name, in the record.

## 4. Generating together
- Everyone adds into the same project from any device: upload pictures, upload a video (the "fewest different pictures" filter),
  or live capture.
- **Names never collide:** each device counts on its own; on sync, a repeated number is moved to the next free one and the XML records
  the rename (method c of the 17.09 note). Or, when online, the device asks the project for the next block of numbers first.
- **Duplicates across members** are flagged on sync by the picture fingerprint, not added twice.
- A **"needed"** card shows the gaps: counts per label and per kind of scene (dusk, close-up, flock), so members fill what is missing.

## 5. Level 1 together — no two people on the same picture
1. **A shared queue of pictures without boxes.** A member taps *Start* and gets the next one; it is held for them (e.g. 10 minutes)
   so nobody else boxes it at the same time. If they leave, it goes back to the queue.
2. Demo.90 (or the latest project model) pre-draws boxes; the member moves the edges, picks names from the label list (with the
   "did you mean" check), saves. The box is **Level 1 · labeled by · time**.
3. Optional **double pass** on a sample (e.g. 1 in 10 pictures boxed by two people independently) to measure agreement before review.

## 6. Level 2 — the second pass for fine-tuning
1. **A review queue of Level 1 boxes**, never showing a reviewer their own boxes.
2. Accept · Fix (edges or name) · Reject with a reason. The box becomes **Level 2 · reviewed by · time**; a fix keeps the old box in
   the XML.
3. Where two Level 1 passes disagree, the reviewer sees both and decides.
4. Reviewers also merge similar names and keep the synonym table.
5. **Only Level 2 boxes are exported** to train the next version of the project model.

## 7. Seeing the team's work
- Per project: pictures, boxes, waiting for Level 1, waiting for Level 2, accepted / fixed / rejected.
- Per member: added, boxed, reviewed, agreement rate — shown as thanks, not as a ranking that pushes speed over care.
- Each model version lists the members who built it and the counts it was trained on.

## 8. Storage and safety (the operator decides where the shared copy lives)
- **Private by default:** a project's pictures and labels are readable only by its members. The reviewers found today's shared
  tables (`supabase/migrations/040_sensor_fusion_pictures.sql`, `041_sensor_fusion_labels.sql`) readable by any guest — group
  projects need per-project member rules before anyone shares pictures of real places or people.
- **Works offline:** members work on the device; work syncs when the connection returns; nothing is lost if a phone is full or
  closes (the file is saved before the screen says saved).
- **One record:** every action is a line in the project record with a time stamp `YYYY.MM.DD_HH.MM..SS`.

## 9. Tests for Grok (pass lines)
| # | Test | Pass |
|---|---|---|
| G1 | Owner invites a contributor by code | the code admits once per person, expires at its time, role = contributor |
| G2 | A guest (not signed in) uses the code | refused for a group project |
| G3 | Two members tap Start on Level 1 at once | they get different pictures |
| G4 | A member leaves a held picture | it returns to the queue after the hold time |
| G5 | A reviewer opens Level 2 | none of their own boxes are offered |
| G6 | Two devices both make bird.1001 offline, then sync | one is renumbered; the XML records it; no file lost |
| G7 | A non-member reads the project's pictures | refused |
| G8 | Export | only Level 2 accepted / fixed boxes; the member list and counts go with the model version |
