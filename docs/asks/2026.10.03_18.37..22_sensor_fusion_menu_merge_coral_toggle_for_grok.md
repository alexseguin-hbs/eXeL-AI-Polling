## The change
1. **Menu becomes:** `1 Sensor Fusion · 2 Stop · 3 Image labeler · 4 Pose` in **both** the page and Python, from **one list.**
   Put the menu in `models.json` (a `menu` block with `id`, `label`, `go`) and have `sf.ts` and both Python copies read it. Never
   type the menu three times, the same rule as the model list.
   - Keep the old ids as aliases so a saved choice or a script still works: `fusion-coral` and `fusion-cpu` → Sensor Fusion;
     `check-coral` and `check-cpu` → Sensor Fusion with the model set to `checkid`. Typing **5** or **6** in Python prints one line,
     "Check ID is now in the model list. Choose Sensor Fusion, then Check ID.", and opens the model list with Check ID marked.
2. **Coral is a setting, not a menu item.** A "Coral" on/off switch goes in the Settings sheet, under the colour scheme. It is Sensor
   Fusion's own row: the shared Settings component gets an optional app slot, and Financial-2525 and the other apps show no Coral row.
   - Default **off**. Remembered on the device (`sf2525-coral`, wrapped in try/catch). Read once when Sensor Fusion starts.
   - **In the browser** the page always runs `detect.tflite`. The switch only decides what a downloaded run or the edge computer uses,
     and the screen says so in one line under the switch: "Coral runs on a computer with the Coral chip. This page uses the processor."
     New words stay English in `AFTER_FILL`.
   - **In Python** the same setting comes from `--coral` / `--no-coral`, else a small `settings.json` beside the script, else off.
3. **No Coral found, Coral on:** never claim Coral. Python catches the delegate failure and prints "No Coral found. Running on this
   computer's processor." It then runs `detect.tflite`, and the run header says "processor", not "Coral". Today this throws and stops.
4. **The header says what is really running.** `SENSOR 1: ON` gains the model and the engine: `Check ID · processor` or
   `Head · Coral`. It is taken from what loaded, never from the switch alone.
5. **Check ID stays an identity model.** It may be picked and run on its own screen. It is never eligible for a control loop (plan Part C).

## The logic as one pure function (so it can be tested twice)
`resolveRun({ menuId, model, coralSetting, chipPresent, runtime })` → `{ go, model, file, engine, note }`, in a pure module
(`lib/sensor-fusion/run.ts`), with the same table in Python (`resolve_run`).
- `runtime = "browser"` → `file = detect.tflite`, `engine = processor`, always.
- `runtime = "edge"` and Coral on and the chip is present → `edgetpu.tflite`, `engine = coral`.
- Coral on and no chip → `detect.tflite`, `engine = processor`, note = the no-Coral sentence.
- An old alias resolves as in change 1.
- An unknown menu id → the menu again, never a run.
