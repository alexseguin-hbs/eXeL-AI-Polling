## MoT reading — how CODEX folds into the backend architecture
CODEX is the **catalog / "which home" layer ABOVE the Home Building Process pro-forma**. The flow becomes:
**pick a CODEX home (pre-approved, pre-designed) → its build cost → the 7-stage developer pro-forma prices the project.**
It adds three things to the backend model:
1. **A home-catalog entity** (`CodexHome`): collection · name · bed · bath · floors · living ft² · gross ft² · a 3D model +
   floor plans · a **pre-approved** flag. Today the app has only 3 models (Cube / Tiny / Eco-Sphere, in SIM_MODELS); CODEX
   is the much larger, filterable catalog those are the first entries of. A catalog is inherently a **backend/DB concept**
   (list, filter, by-collection) — so CODEX **strengthens the case for Option B** (a first-class backend model) over a
   frontend-only list.
2. **A real pro-forma LEVER — "pre-approved".** A pre-approved, pre-designed home is the whole value of CODEX: it
   **shortcuts the Design & Architecture, Structural and Permitting stages** of the pro-forma (less design fee, no bespoke
   structural, a faster/cheaper AHJ path). This is a genuine, honest connection to the $650k / 290-day pro-forma — a
   pre-approved CODEX home should lower those three stages' cost AND duration. **The deltas are NOT to be invented** —
   they are ESTIMATE/REFERENCE until the operator (or ICON data) sets them.
3. **It CONFIRMS the two-area model we already have.** CODEX shows **LIVING SPACE** and **GROSS FLOOR AREA** as two
   distinct figures — exactly our existing `netSqft` (900) vs `grossSqft` (1,296) distinction in canonicalHouseTruth. (Note
