## 1. How the original Pi did it (upstream `De-Risking-Strategies/SensorFusion`)
- **Capture** (`Demo90/TFLite_detection_webcam_api.py:643-681`): the web panel set a name and a count (default limit 2000). Each video
  frame was written with `cv2.imwrite` to `../Pictures/<name>/<name>-sf-img-<N>.jpg`, N counting up from 0, with "Saving File: N" on
  the video.
- **Two faults to not carry over:**
  - The counter restarts at 0 on every capture run (`img_counter = 0`, line ~681), and the code says so: *"dir already exists, so
    overwrite existing (unless we datestamp)"*. A second run of the same name overwrites the first pictures.
  - No zero padding (`-sf-img-9`, `-sf-img-10`), so the files sort out of order.
- **Zip** (`zipdir.sh`, menu 8): zips `/home/pi/SensorFusion/Pictures/<dir>` into `<dir>.zip` in the same folder.
- **Upload** (`upload.sh`, menu 9): asks for an email, the zip, and a description; gets an upload address from a web service, then
  sends the zip there. One zip per set, with who sent it and why.

## 2. How the app does it today (`frontend/app/SensorFusion-2525/sensor-fusion.tsx`)
- `framesFromVideo` / `takeShots` (~673–714) name pictures `<name>-1.jpg`, `<name>-2.jpg` … — **restarting at 1 every time**. Two
  captures named "head" give two `head-1.jpg`; the phone renames one `head-1 (1).jpg`, or the cloud gets two rows with one name.
- `pushCloud` (~703) inserts every picture into one shared table under those same repeating names.

## 3. The naming law — names never overlap
1. **Name form:** `<label>.<NNNN>.jpg` — the label, a dot, a zero-padded number of at least 4 digits: `head.0001.jpg`. Past 9999 it
   simply grows (`head.10000.jpg`); sorting stays right because the number is read as a number, not as text.
2. **The XML twin keeps the same base:** `head.0001.xml` (from the labeler notes).
3. **Next number = highest number already used for that label + 1.** If `head.0001`–`head.1000` exist, the next capture starts at
   `head.1001`. Numbers are never reused, even after a delete (a deleted number stays a gap).
4. **Where "highest used" comes from, in order of trust:**
   - the folder itself, when the device lets the page read it (desktop Chrome / Edge, and the Python program);
   - else a per-label counter kept on the device (`localStorage`, key by label), raised every time a file is written;
   - and on import (Open set / Save set), the page reads the names in the set and raises its counter to the highest it sees.
5. **Two devices, same label (operator decision).** Two phones that both have `head.1000` would both write `head.1001`. Three ways,
   pick one:
   - **(a) one shared counter in the cloud** — every capture asks for the next block (e.g. 40 numbers) first; needs a connection;
   - **(b) a device mark inside the name** — `head.ipA.1001`; never collides, works offline, but changes the name form;
   - **(c) renumber at merge** — each device counts on its own; when a reviewer merges sets, any repeated number is moved to the next
     free one and the change is written in that picture's XML. Works offline, keeps the operator's name form.
   Recommendation: **(c)**, with (a) added later when the cloud is the operator's choice.
6. **The same rule in the Python program** (`sensor_fusion_edge.py`, menu 4): `Home/SensorFusion/Pictures/<label>/`, scan for the
   highest `<label>.NNNN.jpg`, continue from there; never restart at 0.

## 5. Upload — the Pi's shape, kept
1. **One zip per batch**, named by its range: `head.1001-1040.zip`, with a small manifest inside (who, device, model, label, first and
   last number, time stamp `YYYY.MM.DD_HH.MM..SS`, and a description like the Pi asked for).
2. **Upload sends that zip** — not one row per picture into a shared table. Where it goes (a team folder, a cloud store) is the
   operator's decision. The Pi sent it to a private upload address; pictures of people should not be readable by anyone by default.
3. **The screen says "uploaded" only after the upload answers yes.**
