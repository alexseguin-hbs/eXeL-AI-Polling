## Folded after this round

- **CQS no longer locks the session row (Odin).**
  - Concurrent runs now serialise on a transaction advisory lock keyed on the session (`pg_advisory_xact_lock`), which blocks no other writer.
  - Scores, the winner and `is_winner` are written in one transaction, so a reader never sees scores without a winner.
  - **Proofs (live_db):** three parallel `/ai/cqs` calls give one score per answer and exactly one winner. While one session's CQS transaction is open, another writer inserts an answer for the same session in under 2 seconds.
  - **Verified to bite:** with the round-12 `FOR UPDATE` put back, the insert times out and the test fails.
- **Ranking now triggers CQS (Krishna).**
  - The ranking handoff passes the top Theme02 label and the theme level to CQS scoring.
  - Scoring runs inside a savepoint, so a failed CQS run cannot roll back the ranking.
  - **Proof (live_db):** an aggregated ranking writes one CQS score per eligible answer and exactly one winner.
- **The CQS label is written once, as stored (Thoth, Sofia).** The second `html.escape` is gone. The live_db proof asserts the stored label is `Privacy &amp; Trust`.
- **CQS eligibility is filtered in SQL (Thoth).** Session, cycle, PII gate, the Theme02 label and confidence ≥ 95 are all in the query. The rows come back in response order, and only eligible rows are loaded.
- **The public 'login' start is refused (Enki, Sofia).**
  - `POST /sessions/{id}/time/start` with `action_type: "login"` returns 400. Login credit comes only from the join.
  - Every Cube 5 entry now mints by the accumulated-minutes floor, login included.
  - **Proofs:** the live_db route test gets 400 for a public login start. A unit test shows 30 one-second Cube 5 login entries mint 0 ♡.
- **Thor's Cube 2/3 rounding is now an operator decision (HP-38), not a silent fix.**
  - Text and voice entries still mint ceil(minutes) per submission. That is about 1 ♡ + 5 ◬ per answer, however short.
  - Token_Governance_Math.md says floor; CUBES_4-6.md says ceil. HP-38 records both readings and the three options (a: accumulate per participant, b: one ♡ per answer by design, c: a minimum per submission).
  - The economics are the operator's call, so I left the code as it is.
