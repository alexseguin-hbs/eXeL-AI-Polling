# r.213 red-first — the three mouse-look rows, proved able to fail

His ask is **mouse look**: *"allow for mouse controller to operate similar to arrows (to move turret arround)"*, and
then *"the key for this update was using mouse cursor to move the target … that we can later apply to drone and
robotics, as well as fixed wing and foil"*.

**On the r.212 bytes the capability does not exist at all** — `pointerLock`, `movementX` and `KeyM` each occur
**0 times** in the 1.15 MB file — so "insert the rows into the old bytes" would only prove that a call to an
undefined function throws. That is a weaker statement than the one worth making, so each row was instead proved
able to fail by **sabotage of the cut**: the invariant is removed, one edit at a time, and the row must go red.

Measured with `scratchpad/r213/sabotage.sh` on the built r.213 bytes
(sha256 `18a105660b0b12da417f9e211e6c7089e4d680c9209262cfbfee4ddc5c008c41`), 249 boot rows each run.

| # | the invariant removed | rows that went red |
|---|---|---|
| **S1** | the look's sign is flipped (`u.pan-=dx*k` → `+=`) — the mouse would turn the head opposite to the arrows | `MOUSELOOK_TURNS_THE_HEAD_LIKE_THE_ARROWS` |
| **S2** | the left button approves for you — a target fires without having been approved | `MOUSELOOK_CLICKS_ARE_FIRE_AND_TARGET` |

Nothing else went red in any run (`SYNC_DIRECT` is declared), so each row fails for its own reason and not from
collateral damage.

## S4 and S5 are not hypothetical — the sabotage pass found both of them in my own first cut

**S4 was a real defect, caught by the gate before the ship.** The first cut registered the captured-click swallow
**on the canvas** in the capture phase, reasoning that capture runs before bubble. It does — *between nodes*. At the
**target** node the DOM runs capturing and bubbling listeners in **registration order**, and the shipped handlers are
registered hundreds of lines earlier, so a capture listener added in the append zone still runs **second** and cannot
pre-empt them. The symptom was visible in the S3 run: with the handler sabotaged to swallow everything, a synthetic
touch `pointerdown` **still set `state.drag`**. Under a real pointer lock that means the shipped right-button fast
path would have run too, calling `pickNear` on frozen `clientX/clientY` and marking a plate the player is not on.
The swallow now sits on **`window`**, one node up, where the capture phase genuinely is first, and
`MOUSELOOK_LEAVES_THE_TOUCH_PATH_ALONE` asserts that placement by name (`upOneNode`).

**S5 was a hole in my own gate.** The first version of `MOUSELOOK_TURNS_THE_HEAD_LIKE_THE_ARROWS` asserted the
*direction* and the *dial*, and S5 — removing the turret's `fovDeg()/38` scaling, which is half of DD-75 — left all
three rows **green**. A gate that does not defend its invariant is not a gate. The row now also measures the law as
it is lived: zoom to 3× and the turret's degrees per 100 px must shrink, while a QUAD's must not move at all.
