# r.212 — red first

## The gate that was already red on what shipped

`tests/deck-rcore.test.mjs` on the **shipped r.211 bytes** (`frontend/public/drone-2525/play.html` at `689a4a4e9`):

```
FAIL: the deck carries the record through rev 87; the file is exactly one entry longer —
      this release's own row (lag 2, last kind release)

deck-rcore: 91 passed, 1 failed · the range's R-CORE is the shared ledger in the shared format, through rev 87
exit 1
```

This is not a gate written for r.212. It is the gate added at r.210 that **r.211 shipped past**, and it is why
Deploy run #1890 failed, why `ship` was skipped, why the Cloudflare build fell (the deck gates are in `prebuild`
since r.196), and why the site stayed on `df76efa` while Verify Live #2820 polled for ten minutes.

The three numbers behind it:

| | |
|---|---|
| `docs/traceability/drone-2525.ledger.json` | **89** entries (rev 89 = r.211's own release row) |
| the deck's embedded block | `"through":87` |
| `tests/deck-rcore.test.mjs:42-45` | requires `lag === 1` |

89 − 87 = **2**.

## That the chain itself refuses

`r212-execute.sh` runs this gate against the r.211 bytes **before** it patches anything, and **exits 1 if it is
green** — because a green result there would mean the premise of this revision is wrong. The red is a required
step, not an observation.

## Green on the cut

After the patcher regenerates the record through rev 89, and after the bookkeeping appends rev 90, the same gate
runs again in step 4 against the exact bytes commit B carries. Its output is tee'd to a file and quoted in the
notes, rather than transcribed by hand — which is the habit that produced the false `deck-rcore 92/0` in the
r.211 commit message.
