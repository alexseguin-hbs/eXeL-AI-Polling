# High Priority Backlog: 1M live polling feeds + 9-theme voting

For the operator (HI) and the ChatGPT reviewer. Every item the SSSES loop has **not** fixed in code, with evidence and
the fix. Source: docs/asks/*_ssses_loop_apis.md (addenda 1–2), the round-1 reviewer lenses and the 1M scale review
(measured on 1,000,000 real ballots in Postgres 16; scripts in the session scratchpad `scale/`).

Each item has an ID, severity and what it **needs**:
- **CODE**: can be done in the repo.
- **APPROVAL**: touches the protected Trinity files (`dashboard/page.tsx`, `session-view.tsx`, `mock-data.ts`
  `startSpiralTest`), which CLAUDE.md requires to be verified live first.
- **DECISION**: an operator choice.
- **INFRA**: an account, binding or plan change only the operator can make.

## A. Blockers: the live site cannot serve 1M today

| ID | What breaks at 1M | Evidence | Fix | Needs |
|---|---|---|---|---|
| HP-01 | Every response is broadcast to every participant. Participants send `new_response` on `session:CODE` and also subscribe to it, so 1M users × 1 response = 10¹² deliveries. | `frontend/lib/use-session-broadcast.ts:146-166`; `components/session-view.tsx:686,753` | Moderator-only topic (`mod:CODE`). Participants send without joining, via REST broadcast or an edge aggregator batching every 500 ms. Keep `session:CODE` for low-rate control events. | APPROVAL + CODE |
| HP-02 | Poll storm: 1.67M Worker req/s + 0.67–1M Supabase REST req/s during polling. Polls never back off. "Broadcast healthy" resets after 8 s of silence. | `session-view.tsx:561,597-656`; `join-flow.tsx:258`; `mock-data.ts:1143,1178` | Health = socket SUBSCRIBED, not traffic. Moderator heartbeat every 15–30 s. Exponential backoff with jitter (1.5→30 s). Drop the duplicate KV fetch. CDN-cacheable status (`s-maxage=2`). | APPROVAL + CODE |
| HP-03 | Deployed voting is per tab. The live site runs `MOCK_MODE=true` (deploy.yml never sets it), and `_rankingBallots` is an in-memory Map per tab, so phones never share ballots. | `lib/api.ts:10`; `mock-data.ts:826,1361-1405`; `.github/workflows/deploy.yml` | Route `POST /rankings` to a hosted backend, or at minimum to a shared Supabase table with a database-side tally. | DECISION + INFRA |
| HP-04 | Moderator dashboard is quadratic: `[{...}, ...prev]` per response plus an unvirtualised list. Measured 100k responses = 96.6 s; the tab saturates around 30k. | `dashboard/page.tsx:245-251,789,946` | Ring buffer (last 500) + separate count + virtualised list + `setState` batched every 250 ms. | APPROVAL + CODE |
| HP-05 | Aggregation at 1M: 71.8 s and 3.46 GB per run (two full ORM loads plus an O(N) replay-hash string). | `ranking_governance.py:427-437`; `ranking_aggregation.py:157-195,284` | SQL aggregate (`jsonb_array_elements WITH ORDINALITY` grouped by theme) or `BordaAccumulator`. Order-independent streaming replay hash over the ordering→count table (≤362,880 rows). **Changes the stored replay-hash format.** | DECISION (determinism contract) + CODE |
| HP-06 | Supabase Realtime caps: around 10k connections and about 2.5k msg/s below Enterprise. 1M sockets needs Enterprise, Cloudflare Durable Objects, or an Ably/Pusher-class tier. | Supabase published quotas | Choose and provision the fan-out tier. | INFRA |
